# RagMind · 评测方案

> RAG 系统最反直觉的一点：**「看起来答对了」和「真的答对了」是两回事。**
> 评测的目的不是给系统打分，而是**告诉你下一刀该砍在哪——是检索漏了，还是生成编了。**

---

## 1. 评测分层

RAG 要分两层独立评测，否则出了错无法归因：

| 层 | 问的问题 | 指标 |
|---|---|---|
| 检索层 | 正确的 chunk 有没有被捞上来？ | recall@k、MRR、命中率 |
| 生成层 | 捞上来之后，答案对不对、有没有编？ | faithfulness、answer relevance、正确率 |

**归因逻辑**（面试必考）：

```
retrieval 低 + generation 低  → 先修检索（垃圾进垃圾出）
retrieval 高 + generation 低  → 修 prompt / 换模型 / 加溯源约束
retrieval 高 + generation 高  → 及格，继续做生产化
```

---

## 2. 评测集设计

**规模**：30–50 条起步（通用版），做深入再加到 100+。
**每条必须包含**：

```json
{
  "question": "生产环境 Redis 内存告警，第一步该做什么？",
  "reference_doc": "redis-ops.md",        // 标准答案所在文档
  "reference_chunk": "chunk_00123",       // 标准答案所在 chunk（可选，用于 recall）
  "answer": "先看 maxmemory 和淘汰策略……",  // 人工标准答案（用于判分）
  "distractors": ["redis-基础概念.md", "mysql-运维.md"]  // 干扰文档，测检索能否排除
}
```

**为什么要干扰文档**：没有干扰项，检索随便召回都"命中"，测不出区分度。

---

## 3. 指标与实现

### 3.1 检索指标

```python
recall@k = 检索 top-k 里是否包含 reference_chunk 的比例（k=5 常用）
MRR      = 正确答案排名的倒数（越靠前分越高）
```

实现：`scripts/eval_ragas.py` 里用 `core/retrieval.py` 直接检索，不经过 LLM。

### 3.2 生成指标（要 LLM 判分，RAGAS 或自写 judge）

| 指标 | 含义 | 怎么判 |
|---|---|---|
| faithfulness（忠实度） | 答案是否**只**基于检索出的上下文 | LLM-as-judge：答案里的每个陈述能否从上下文推出 |
| answer relevance | 答案是否真的回答了问题 | LLM-as-judge |
| context relevance | 检索出的上下文是否和问题相关 | LLM-as-judge |

**为什么忠实度最重要**：它直接对应「幻觉」。忠实度低的答案即使"看起来对"，也是不可信的。

### 3.3 判分器的局限

LLM-as-judge 本身会偏（偏好长答案、偏好流畅答案）。缓解：判分 prompt 写清标准、
同一批用同一 judge 对比（相对分比绝对分可信）。

## 4. 评测执行

```bash
make eval          # 跑完整评测
make eval-retrieval  # 只跑检索指标（快，适合每次改完就跑）
```

**纪律**：任何一次优化（改分块、改权重、改 prompt）**必须用同一评测集重跑**，出对比表。
没有对比的优化 = 没有发生。

## 6. 失败样本分析（比总分更有价值）

总分从 0.7 到 0.8，你只知道「变好了」。真正值钱的是**逐条看失败样本**：

| 失败问题 | 失败在哪一层 | 根因 | 解法 |
|---|---|---|---|
| 「登录不上」 | 检索 | 文档用「认证失败」，语义没对上 | 加查询改写 / 同义词 |
| 「E1001 错误」 | 检索 | 纯向量对错误码不敏感 | 混合检索全文补 |
| 「今年预算」 | 生成 | 检索到去年的文档 | 元数据时间过滤 |

**面试亮点**：能拿出 3 个具体的失败样本并说清根因和解法，比报一个 0.85 的总分强十倍。

## 7. 评测平台化（可选 W3）

把 `make eval` 做成 CI 门禁：**PR 里改了 prompt / 分块 / 权重，评测分下降超过阈值就拦下合并。**
这是「AI 工程质量」的最强证据——评测不是跑一次，是每次变更都要过。

```yaml
# .github/workflows/eval.yml 的伪逻辑
on: pull_request
jobs:
  eval:
    steps:
      - run: make eval
      - run: python scripts/check_eval_gate.py --min-faithfulness 0.8
        # 低于阈值 → exit 1 → CI 红
```
