# RagMind · 设计决策与取舍

> 回答 AI 工程师最常被追问的问题：**「为什么这么设计？」**
> 每个决策都要求：选项 → 依据 → 代价 → 什么情况下推翻。

---

## 1. 为什么用 pgvector 而不是专用向量库（Qdrant / Milvus / Chroma）

| 维度 | pgvector | 专用向量库 |
|---|---|---|
| 向量检索能力 | 好（HNSW/IVFFlat） | 更强（更多索引类型、更大规模） |
| 元数据过滤 | 原生 SQL，和向量同库 JOIN | 各自语法，跨系统 JOIN 困难 |
| 全文检索 | PostgreSQL 原生，可混合 | 通常要另接 |
| 运维成本 | 你已有 PG 运维能力 | 新系统、新故障模式 |
| 数据一致性 | 单一事实来源 | 双写、同步问题 |

**决策**：pgvector。

**核心理由**：真实 RAG 的查询**极少是纯向量**——几乎总有「只看某个产品线 / 只看某类文档 / 关键词精确匹配」
这类元数据和全文条件。向量库擅长相似度，不擅长「向量 + 元数据 + 全文」的组合查询。
把三者放进同一个 PostgreSQL，用一个 SQL 搞定，**避免了一个最容易翻车的分布式一致性问题**。

**代价**：单机向量规模上限低于专用库（百万到千万级 chunk 尚可，亿级要分片）。
**推翻条件**：chunk 数 > 5000 万，或需要按向量做超大规模 ANN 且元数据过滤很少。

> 这个答案的妙处：它和你的架构师项目（海量数据库调优）**无缝衔接**。
> 你能接着讲「pgvector 的 HNSW 索引在多少维、多少数据下开始退化」，这是纯 AI 背景的人讲不出的。

## 2. 分块策略：由评测集决定，不是拍脑袋

**选项**：

| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 固定长度 | 512 token，重叠 10% | 简单、可复现 | 切断语义 |
| 语义分块 | 按标题/段落/列表边界 | 语义完整 | 长度不可控，短文档切太碎 |

## 3. 混合检索：向量 + 全文

**为什么纯向量不够**：向量擅长「意思相近」，但对**精确标识符**（错误码 `E1001`、产品型号、
API 名 `POST /v1/users`）不敏感——而这些问题在技术知识库里占比很高。

**为什么纯全文不够**：全文能精确命中关键词，但用户问「怎么登录不上」匹配不到文档里的
「认证失败排查」，丢掉了语义。

**融合方式**（可复现的）：

```
score = α · 归一化向量相似度 + (1 - α) · 归一化全文相关度
```

α 的取值**用 recall@k 曲线扫出来**，默认 0.6（向量为主、全文补漏）。

## 4. 重排：用更贵的模型只算 top-20

**问题**：向量检索 top-5 里正确答案可能排第 3，但被截断。扩大 top-k 又增加噪音和生成成本。

**方案**：检索先召回 top-20（便宜、粗），再用 cross-encoder 或 LLM 重排到 top-5（贵、准）。

**为什么只重排 20 条**：重排成本 ∝ 候选数，但边际收益递减。20 → 5 的重排，比 100 → 5
省 5 倍成本，质量几乎无损。

**代价**：多一跳重排，延迟 +[X] ms。可用「只在混合检索置信度低时触发重排」来省。
**推翻条件**：如果检索已经很准（recall@20 接近 1），重排收益趋零，可以去掉。

## 5. 查询改写

**为什么需要**：
- 口语化：「上次说的那个怎么配」→ 需要补上下文
- 指代：「它支持哪些字段」→ 「它」指什么

**做法**：先用 LLM 把问题改写成一个**自包含、明确**的检索查询（保留原意）。
**代价**：多一次 LLM 调用，延迟 +[X] ms、成本 +[X]。
**省法**：简单问题（能直接命中缓存 / 检索置信度高）跳过改写。

## 6. 语义缓存 vs 普通缓存

**普通缓存**（按原始字符串）命中率低——「怎么登录」「如何登录」「登录不上」是三个 key。
**语义缓存**（按嵌入相似度 > 0.95）能把上面三个合并命中。

**代价**：每次查缓存要先算一次嵌入（比查字符串贵），但比检索+生成便宜一个数量级。
**风险**：相似度阈值太高漏命中、太低错命中。阈值也用评测集标定。
**新鲜度**：TTL 越短越准、越省不了钱。热点 FAQ 可以长 TTL，时效性内容（如「本周发布」）禁用缓存。

## 7. 提示模板版本化

prompt 是「代码」，也要版本管理：

```
prompts/
  answer_v1.yaml   # 基础版
  answer_v2.yaml   # 加了溯源约束
```

**为什么**：改了 prompt 会同时影响忠实度、延迟、成本。不版本化，就没法做
「v2 比 v1 忠实度 +0.1，成本 +5%」的对比，也没法回滚。
